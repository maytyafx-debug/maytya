# استاندارد طراحی رابط و تجربه کاربری متاتیا

نسخه: 1.0  
وضعیت: استاندارد اجرایی پروژه  
دامنه: وب‌سایت فعلی Metatya و محصولات وب؛ راهنمای توسعه برای اپ‌های Android و iOS در آینده

## 1. تصمیم محصول و دامنه

متاتیا در حال حاضر یک وب‌سایت استاتیک مبتنی بر HTML، CSS و JavaScript است که از GitHub Pages در پوشه `docs/` منتشر می‌شود. بنابراین:

- اولویت اجرایی فعلی: وب واکنش‌گرا با رویکرد mobile-first؛ نه ساخت اپ بومی فرضی.
- رابط وب باید روی موبایل اندروید، Safari آیفون، تبلت و دسکتاپ قابل استفاده باشد.
- SwiftUI فقط هنگام ایجاد اپ بومی iOS وارد پروژه می‌شود.
- Jetpack Compose و Android Skills فقط هنگام ایجاد اپ بومی Android وارد پروژه می‌شوند.
- تا زمانی که معماری پروژه تغییر نکرده، وابستگی React، Next.js، Tailwind یا Motion صرفاً به دلیل پیشنهاد یک کتابخانه اضافه نشود.
- هر کامپوننت بیرونی باید با ساختار فعلی سازگار، دارای مجوز روشن، سبک، قابل نگهداری و قابل دسترس باشد.

## 2. هویت بصری متاتیا

هویت بصری باید یکپارچه بماند، اما تمام صفحات نباید یک قالب تکراری داشته باشند.

### توکن‌های پایه

- پس‌زمینه اصلی: `#050807`
- سطح و پنل: `#0C1511` و `#101D17`
- سبز امضای برند: `#00FF9D`
- طلایی: `#D6AD45`
- طلایی روشن: `#F3D98B`
- متن اصلی: `#F2F5F2`
- متن ثانویه: `#9AA9A0`
- خط جداکننده: طلایی با شفافیت کم

قواعد:
1. سبز برای اقدام یا وضعیت مثبت معنادار؛ نه تزئین همه اجزا.
2. طلایی برای هویت، تاکید و جزئیات ممتاز؛ نه متن طولانی.
3. کنتراست متن، فوکوس صفحه‌کلید و خوانایی فارسی بر جلوه بصری مقدم‌اند.
4. Vazirmatn فونت پیش‌فرض فارسی فعلی است؛ جایگزینی آن فقط با آزمون واقعی خوانایی انجام شود.
5. هر صفحه باید یک ایده بصری شاخص داشته باشد؛ اما از گرادیان، کارت‌های هم‌شکل، شیشه‌ای‌کردن همه سطوح و انیمیشن بی‌دلیل پرهیز شود.

## 3. فرایند طراحی پیش از کدنویسی

برای هر صفحه یا بازطراحی مهم، ابتدا یک Design Brief کوتاه ثبت شود:

- هدف اصلی صفحه و مهم‌ترین اقدام کاربر چیست؟
- مخاطب و سطح آشنایی او با موضوع چیست؟
- مهم‌ترین اطلاعاتی که باید در نگاه اول فهمیده شود چیست؟
- صفحه در موبایل چگونه اولویت‌بندی می‌شود؟
- چه چیزی این صفحه را از یک قالب عمومی AI متمایز می‌کند؟
- چه داده‌ها و قابلیت‌هایی واقعی‌اند و کدام هنوز آماده نیستند؟

پس از آن:
1. مسیر و سلسله‌مراتب محتوا را طراحی کن.
2. توکن‌های رنگ، تایپوگرافی، فاصله و شعاع را از سیستم متاتیا بگیر.
3. یک الگوی چیدمان متناسب با هدف انتخاب کن؛ همه صفحات را به کارت‌های سه‌تایی تبدیل نکن.
4. حالت‌های loading، empty، error، success، disabled و focus را طراحی کن.
5. سپس پیاده‌سازی کن و در اندازه‌های مختلف بازبینی کن.

## 4. قواعد تجربه کاربری و دسترس‌پذیری

- ابتدا برای عرض 360 تا 390 پیکسل طراحی کن؛ سپس تبلت و دسکتاپ.
- از `viewport-fit=cover` و safe-area فقط در جایی که لازم است استفاده کن.
- اندازه هدف لمسی ترجیحاً حداقل 44×44 پیکسل باشد.
- تمام کنترل‌ها با صفحه‌کلید قابل دسترسی باشند و focus-visible واضح داشته باشند.
- برای فرم‌ها label واقعی، پیام خطای قابل فهم و حفظ داده واردشده فراهم کن.
- رنگ تنها راه انتقال وضعیت نباشد؛ متن یا نشانه مکمل ارائه شود.
- برای تصاویر معنادار alt مناسب و برای تزئینات alt خالی استفاده شود.
- از حرکت غیرضروری، parallax سنگین و چشمک‌زدن پرهیز کن.
- `prefers-reduced-motion` را رعایت کن؛ محتوا بدون انیمیشن نیز باید کامل باشد.
- متن فارسی راست‌چین، اعداد و نمادهای لاتین در جای درست و لینک‌ها واضح باشند.
- عملکرد در اینترنت ضعیف، بارگذاری فونت و تصاویر، و جلوگیری از layout shift بررسی شود.

## 5. حرکت و انیمیشن

حرکت باید به فهم وضعیت، بازخورد تعامل یا روایت محصول کمک کند.

- حرکت‌های کوتاه و قابل قطع را ترجیح بده.
- برای ورود و خروج از opacity و transform استفاده کن؛ از انیمیشن مداوم layout پرهیز کن.
- حرکت‌های hover نباید برای لمس ضروری باشند.
- برای دکمه‌ها بازخورد pressed، loading و success واضح طراحی شود.
- انیمیشن‌های تزئینی در صفحات آموزشی و داشبوردها محدود باشند.
- هر انیمیشن باید fallback بدون حرکت داشته باشد.

## 6. سیاست استفاده از مهارت‌ها و منابع معرفی‌شده

### مناسب برای جریان فعلی وب

- **Anthropic frontend-design**: مرجع فرایند انتخاب جهت هنری، تایپوگرافی و پرهیز از ظاهر کلیشه‌ای. از اصول آن استفاده می‌کنیم، نه اینکه بدون بررسی ابزار یا افزونه‌ای را نصب کنیم.
- **ui-ux-pro-max**: مرجع کمکی برای بررسی الگوهای UX، پالت، تایپوگرافی، نمودار و سازگاری با پلتفرم. پیشنهادهایش باید با برند و ساختار واقعی پروژه تطبیق داده شوند.
- **Taste Skill**: ایده‌ی بازبینی پیش از طراحی، تعیین شدت حرکت و تراکم بصری و بررسی خروجی در مرورگر مفید است. نسخه جدید آن experimental است؛ بنابراین قواعد سخت‌گیرانه‌اش به‌صورت پیش‌فرض بر کل پروژه تحمیل نمی‌شود.
- **Emil Kowalski skills**: مرجع تخصصی برای واژگان حرکت، timing، easing و ریزتعامل‌ها؛ انیمیشن فقط در صورت ارزش UX اضافه شود.

### فقط برای اپ بومی آینده

- **Google Android Skills**: مخزن رسمی Android برای گردش‌کارهای مشخص Android و Jetpack Compose؛ هنگام ساخت اپ Android از مهارت مرتبط با همان کار استفاده شود.
- **Material 3**: مرجع طراحی Android و کامپوننت‌های بومی. مهارت جامعه‌محور `material-3-skill` جایگزین مستندات رسمی Material نیست و باید جداگانه ارزیابی شود.
- **SwiftUI Expert Skill**: راهنمای جامعه‌محور برای پیاده‌سازی SwiftUI؛ در اپ iOS، مستندات Apple و Human Interface Guidelines مرجع نهایی باقی می‌مانند.

### کتابخانه‌های کامپوننت و رفرنس

- **Vengeance UI**: منبع الهام برای تعامل‌های خاص و بلوک‌های بازاریابی؛ هر قطعه باید از نظر مجوز، وابستگی و کارایی بررسی شود.
- **Animate UI**: برای پروژه‌های React مبتنی بر Radix، Base UI یا React Aria مناسب‌تر است؛ کد آن را مستقیم وارد سایت HTML فعلی نمی‌کنیم.
- **UILora**: مجموعه‌ای برای React و React Native با اجزای رایگان و پولی؛ فقط نمونه‌های مجاز و متناسب بررسی شوند. وابستگی تجاری یا پولی بدون ضرورت اضافه نشود.
- **LottieFiles**: برای حرکت‌های برداری سبک و قابل استفاده در وب و موبایل گزینه‌ی قابل بررسی است؛ فقط فایل‌های دارای مجوز روشن و با fallback استفاده شوند.
- **Spline**: فقط برای یک صحنه سه‌بعدی شاخص در صفحه‌ای که واقعاً به آن نیاز دارد؛ نه برای پس‌زمینه همه صفحات. حجم، زمان بارگذاری، مصرف GPU و fallback دوبعدی باید بررسی شود.
- **Streamline**: اگر آیکون لازم شد، مجوز هر مجموعه و شرایط استفاده تجاری بررسی شود.
- **Frameline**: تا وقتی نشانی رسمی و منبع قابل راستی‌آزمایی مشخص نشده، وارد فهرست وابستگی‌ها نمی‌شود.

## 7. قانون انتخاب کامپوننت

پیش از افزودن هر کامپوننت:
1. آیا مشکل واقعی کاربر را حل می‌کند؟
2. آیا با HTML/CSS/JS فعلی سازگار است؟
3. مجوز و امکان استفاده تجاری روشن است؟
4. آیا نیاز به حساب، هزینه، کلید یا سرویس خارجی دارد؟
5. آیا دسترس‌پذیر و واکنش‌گراست؟
6. آیا حجم و زمان بارگذاری قابل قبول است؟
7. آیا می‌توان آن را بدون قفل‌شدن به فروشنده نگهداری کرد؟

اگر پاسخ یکی از موارد حیاتی روشن نیست، کامپوننت اضافه نشود. در صورت امکان، کد کوچک و بومی پروژه بر افزودن یک فریم‌ورک کامل ترجیح دارد.
